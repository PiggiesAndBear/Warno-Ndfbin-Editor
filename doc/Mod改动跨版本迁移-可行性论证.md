# Mod 改动跨版本迁移 —— 可行性论证

> **本文只论证，不实现。**
> 问题：本编辑器能否记录对某个 Mod 的累计操作，使得 Mod（或游戏）更新后，
> 把老版本的改动快速搬进新的 ndfbin？
>
> 结论依据全部来自本仓库代码实测与真实 mod 文件，不含推测；推断部分单独标注「推断」。

---

## 结论先说

**技术路线支持，但当前代码只完成了一半，而且缺的那一半不是加个功能就有的。**

| | 状态 |
|---|---|
| 「改了什么」算得准不准 | ✅ 精确到字段、精确到一步 |
| 这份数据能不能存下来 | ❌ 只在内存，保存后清空 |
| 能不能按它找到新文件里的同一个对象 | ❌ 现在用的 id 是位置序号，换文件即失效 |
| 有没有可用的稳定标识 | ✅ **顶层对象有全局唯一 GUID**（实测 2268/2268 唯一） |
| 新增对象能不能重建 | ✅ 克隆 + 加字段的写入路径已经跑通（AG 页在用） |

一句话：**「记录」缺持久化层，「迁移」缺寻址层。前者是工程活，后者有一块硬骨头（新增对象）。**

而 GUID 的存在，是这条路线**技术上成立**的物理基础 —— 没有它，跨版本迁移只能靠名字猜，那是不可靠的。

---

## 一、先分清「Mod 更新」是哪一种

这三种情况的难度差一个数量级，不能混着讨论：

| 情况 | 谁在更新 | 对象 GUID 稳不稳 | 难度 |
|---|---|---|---|
| **A. 游戏本体更新** | Eugen | 原版对象的 GUID 写在 `.ndf` 源码里，**推断**不变 | 中 |
| **B. 同一个 mod 出新版** | mod 作者（你自己或别人） | 作者不重新生成 GUID 就**稳定** | 低 |
| **C. 别人的 mod 大改版** | 陌生作者 | 可能重命名、重建、重新分配 GUID | 高 |

- **B 是主要场景**，也是本文的重点。你改的是自己的 mod，更新后 GUID 自然保持。
- **A** 依赖 `UpdateMod.bat` 的行为：它把工程数据升到新版本，理论上保留作者写的 GUID。
  但游戏若增删了字段，会有结构漂移（见第五节）。
- **C** 不该承诺。别人可以随时重写自己的 mod，声明"能自动迁移"会兑现不了。

> 下文默认讨论 **B**，A 作为附带场景，C 明确排除。

## 二、现有代码逐项核对

| 能力 | 现状 | 证据（文件:行） | 差什么 |
|---|---|---|---|
| 改动检测 | ✅ 精确到字段与列表项 | `history.py` 脏状态差分 | — |
| 改动粒度 | ✅ 一次提交 = 一步 | `Step.delta` 结构 | — |
| 结构改动（加/删字段） | ✅ 用「键在不在」表达 | `Field.added` | — |
| 新增对象 | ✅ 记为 `_APPEND` 状态 | `history.py` `_APPEND_SLOT` | — |
| **持久化** | ❌ 纯内存 | `History` 随文档重建；保存后重新加载即清空 | 全部 |
| **跨文件寻址** | ❌ `object_id` 是位置序号 | `cndf_layout.py:223` `{"id": len(result)}` | 全部 |
| **稳定标识** | ✅ 顶层实体有 GUID | `DescriptorId` 类型 `guid`(26) | 模块层要自建 |
| 引用解析 | ✅ trans_ref 路径 + obj_ref | `refs.py` | 需按 GUID 重建 |
| 克隆写入 | ✅ clone-on-write 已跑通 | `ag_edit.py` | 需记录模板来源 |
| 原子保存 + 备份 | ✅ 一次性 `.bak` | `writer.py:247` | `.bak` 只留首次 |
| 结构 diff（参考） | ⚠️ 仅牌组专用 | `differ.py` | 不能直接复用 |

### 两个必须点明的实现细节

**① `object_id` 是位置序号，不是身份。**

```python
# cndf_layout.py:223
result.append({"id": len(result), "name": name, ...})
```

第 0 个解出来的对象 id=0，第 1 个 id=1。**任何增删都会让后面的全部偏移。**
`Step.delta` 却是以 `object_id` 为键的 —— 所以一份 delta 只对「生成它的那个文件」有意义。

**② `differ.py` 已经踩过这个坑，还得出了量化结论。**

它的注释里写得很清楚：Test 比 Berlin 少 58 个 deck，**所有引用索引整体平移**，
直接比较索引得到 **2213 个假差异**。所以它对比引用时「只记类型、不记数值目标」。

这段经验是本论证最有力的实证：**跨文件比较，任何基于位置的东西都不可用。**

## 三、为什么不能直接重放 `Step.delta`

三个各自独立、任一存在就足以否决的阻断：

1. **键是位置序号** —— 新文件里 `object_id=42` 可能是完全另一个对象。
2. **值里含旧的对象引用** —— `_REF` 状态存的是旧叶子字典（带旧 `object_id`、`class_id`），
   `_LIST` 存整条旧列表，直接写进新文件会指向错对象，甚至 `decode` 拒绝。
3. **保存后历史清空** —— `history.py` 明确写「保存是提交点，不是可撤销操作」。
   而迁移发生在"保存之后、Mod 更新之后"，那时历史早没了。

所以：**`Step` 是一个很好的"当下表达式"，但不是"可携带的补丁"**。
要迁移，必须换一种表达。

## 四、可行的技术形态：GUID 锚定的语义补丁

思路很简单：**把 delta 翻译成「不依赖位置的描述」，落成一个文件；应用时在新文件里按 GUID 反查。**

### 4.1 为什么 GUID 够用

实测柏林 mod 的 `Pawn.ndfbin`：

```
DescriptorId 出现 2268 次，类型 guid(type_id=26)
有 DescriptorId 的对象 2268 / 18285
唯一值 2268 个，重复 0 个
```

2268 正好等于 `TEntityDescriptor` 数量 —— **每一个顶层实体都有唯一 GUID**。

剩下的 16017 个对象（模块、效果、字段载体）没有 GUID，但它们都挂在某个顶层对象下面，
可以用「父 GUID + 类名 + 同名第 N 个」定位。

> 这与 `differ.py` 的教训一致：**能不用位置就不用，非用不可时加上父级锚点。**

### 4.2 补丁长什么样

```jsonc
{
  "format": "warno-ndfbin-patch/1",
  "file": "GFX/Pawn",                      // 逻辑文件，不是磁盘路径
  "base": { "objects": 18285, "sha256": "…" },   // 生成补丁时的基线
  "edits": [
    // ① 标量字段
    { "kind": "field", "target": "guid:ccffdf1a…", "name": "MaxSpeedInKmph",
      "old": 500, "new": 620 },

    // ② 引用（目标也用 GUID）
    { "kind": "ref", "target": "guid:…", "name": "BackgroundTexture",
      "old": "guid:…", "new": "guid:…" },

    // ③ 引用列表（整条替换，顺序有意义）
    { "kind": "ref_list", "target": "guid:…", "name": "ModulesDescriptors",
      "new": ["guid:…", "guid:…", "guid:…"] },

    // ④ 新增对象（最麻烦的一类，见第五节）
    { "kind": "new_object", "guid": "guid:…", "class": "TStrategicMovementModuleDescriptor",
      "cloned_from": "guid:…",           // 模板是谁
      "fields": { "DeploymentShiftGRU": 7250 } }
  ],
  "unresolved": [ … ]                      // 生成时就无法表达的条目，显式留痕
}
```

关键设计点：

- **`target` 一律是 GUID，不是 id。**
- **每条都带 `old`** —— 这是冲突检测的依据（见 5.3），也是"应用时发现基线变了"的依据。
- **`unresolved` 必须落盘**，不能静默丢弃。这与本项目一贯的「对不上的要收集」原则一致。

### 4.3 应用算法

```
1. 加载新 ndfbin，建两张索引：guid → object_id、以及 (父guid, 类名) → [object_id…]
2. 读补丁，逐条解析 target
3. 每条先比对 old：
     - 新文件里的当前值 == old   → 直接写 new
     - 新文件里的当前值 != old   → 记为冲突，进报告，默认不写
4. new_object：在新文件里克隆 cloned_from，改 GUID，套 fields，
   再按补丁里的引用关系重定向
5. 全部处理完，输出一份「应用报告」：成功 / 冲突 / 目标丢失 / 无法表达
6. 用户确认后才写盘（复用 writer 的原子写 + 备份）
```

**第 5 步的报告是这套东西的核心价值**，不是附属品。跨版本迁移永远会有对不上的条目，
让人一眼看出「哪 3 处需要手工看一眼」，比"全自动但悄悄出错"有用得多。

## 五、四个难点，按难度排序

### 5.1 新增对象的迁移 —— 最硬

AG 页的 clone-on-write 会造出新对象（新 `object_id`、新 GUID）。旧补丁里它存在，
新文件里没有。要重建它需要：

- 记录**克隆自谁**（模板 GUID）—— 模板本身可能在新版被删/改
- 记录**完整字段集**，而不只是改动项（因为新文件里没有它）
- 重建后**重定向所有指向它的引用**（别的对象可能引用了这个克隆体）

风险：如果模板在新版里结构变了（字段被删），克隆出来的东西不完整。
**这一块只能做到"尽力重建 + 明确报告"，做不到保证。**

### 5.2 引用重定向

补丁里存 GUID 是干净的，但落地时要转成新文件的 `object_id`。
麻烦在于**被引用的对象可能在新版里不存在**（作者删了、重命名了）。

处理：解析失败就记进报告，**不要退回按位置猜** —— 那正是 `differ.py` 记录的
2213 个假差异的来源。

### 5.3 冲突检测（三方合并）

你的改动把某字段从 10 改成 20；新版作者把它从 10 改成 15。谁赢？

补丁里带 `old=10`，所以应用时能判断：

| 新文件当前值 | 判定 | 动作 |
|---|---|---|
| == `old` | 无冲突 | 写入 `new` |
| == `new` | 已经是目标值 | 跳过 |
| 其它 | **冲突** | 不写，报给用户 |

这是标准的**三方合并**（基线 = `old`）。只做两条路（"有冲突就停"）比自动猜更安全。

### 5.4 结构漂移

游戏更新可能：删字段、改字段类型、改列表约束、改枚举取值。
这些都属于「补丁表达不了」，只能报出来。

## 六、另一条路：不做记录，做「基线比对」

如果不想动编辑流程，还有一条更省事的路：

```
旧版文件  ──┐
            ├─ diff ──> 补丁 ──> 应用到新版文件
基线原版  ──┘
```

- **不在编辑器里记任何东西**
- 需要迁移时，拿「旧版 mod 文件」和「基线原版文件」比一次，得到改动集合
- 再把改动集合应用到「新版文件」

### 优点

- **完全不动现有编辑链路**，纯离线工具，可以单独一个脚本/GUI 入口
- `writer.py` 已经保留**一次性 `.bak`**（首次保存前的原始文件）—— 基线天然存在
- `differ.py` 证明了这个项目已经会做「结构化比对」，只是目前只针对牌组

### 缺点

- 必须有基线文件。`.bak` 只保留第一次保存前的，多次保存后就不再是"原版"
- 需要一个"哪份是基线"的约定，或者让用户手动指定

### 对比

| | 记操作（方案一） | 比基线（方案二） |
|---|---|---|
| 改动编辑链路 | 要改（加持久化） | 不动 |
| 需要基线文件 | 不需要 | **需要** |
| 能回答「改过几次、按什么顺序」 | ✅ | ❌ 只有最终态 |
| 实现量 | 大 | 小 |
| 适合谁 | 长期维护自己 mod 的人 | 偶尔迁移一次的人 |

**两者不冲突**：方案二的产物（补丁）和方案一的产物是同一种格式。
推荐**先做方案二**，因为它不改编辑器，而且能把"补丁格式 + 应用器 + 冲突报告"这套
核心先验证一遍；跑顺了再决定要不要让编辑器在编辑时顺手记补丁。

## 七、还要回答的一个现实问题：改动跨多个 ndfbin

一个 mod 的改动通常散落在几个逻辑文件里（`GFX/Unit`、`GFX/Weapon`、`GFX/EffectCapacity`）。
补丁必须**按逻辑文件分组**，不能混成一个：

- 每个逻辑文件有自己的对象表、自己的 GUID 空间
- 新版本里某些文件可能没变（那就整份跳过）
- 应用时逐个文件独立处理、独立报告

补充补丁格式里 `"file": "GFX/Pawn"` 这一项就是为此。

## 八、工作量与风险

| 部分 | 量级 | 风险 |
|---|---|---|
| 补丁格式 + 生成（从两份文件 diff） | 小 | 低 —— 复用现有解码器 |
| 补丁应用器 + 报告 | 中 | 中 —— 冲突判定逻辑要写对 |
| 新增对象重建 | **大** | **高** —— 模板漂移、引用重定向 |
| 编辑器内持久化操作记录 | 中 | 中 —— 要处理"保存点"语义 |
| 接入 GUI | 中 | 低 |

风险最高的一处：**新增对象**。如果只做"改现有对象的值"，这套东西可以做到接近可靠；
一旦涉及克隆，就进入"尽力而为"的区间。

**建议第一版明确只支持前四类里的前三类**（字段 / 引用 / 引用列表），
新增对象先报"需要手工处理"，把不可靠的部分挡在外面。

---

## 九、结论与建议顺序

**结论：可行，但要分层交付，不能一次做成"全自动迁移"。**

1. **第一步（建议先做）**：补丁格式 + `diff` 生成器 + 应用器 + 报告，
   只支持改值/换引用，不碰新增对象。用真实 mod 更新验一次。
2. **第二步**：补上新增对象的重建（尽力而为 + 报告）。
3. **第三步**：再考虑要不要让编辑器在编辑时顺手记补丁（方案一），
   让"没有基线文件"也能迁移。

如果第一步在真实场景里就发现对不上的条目太多（比如 GUID 因为作者重建而变化），
那么后面的都不用做了 —— **这个验证花不了多少工，但能省掉一个方向性的误判。**

---

## 十、明确不能承诺的

写在这里，是为了避免以后对功能期望过高：

- **不能保证 100% 自动。** 冲突、目标丢失、结构漂移都会需要人看一眼。
- **不能处理"别人重写了自己的 mod"。** GUID 变了就是另一个对象，任何工具都无法判定它们是同一个。
- **不能恢复"改了几次、按什么顺序"**（除非做方案一）。
- **不能替代真机验证。** 补丁应用成功 ≠ 游戏表现正确。
