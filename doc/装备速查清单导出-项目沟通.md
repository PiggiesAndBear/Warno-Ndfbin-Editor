# 装备 / Pack 速查清单 —— 从 mod 的 ndfbin 一键导出

> **状态**：沟通稿，等拍板（未开工）
> **日期**：2026-10-19
> **样本 mod**：`A World in Flames`（workshop `3388575848`，18 个 ndfbin、「大量新单位」）
> **参考产物**：`Equipment_Pack_Lookup.html`（1.3 MB 单文件，由 `gen_equipment_lookup.py` 从 `.ndf` 源码生成）
> **目标读者**：本项目后续实现者（含未来的自己）

## 0. 一句话

现在已经有一套「从 `.ndf` 源码 + base.zip 生成速查表」的工具。这次要做的是**同一份表，但数据从 mod 编译后的 `.ndfbin` 二进制读**，以便反映你正在改的那个 mod，而不是出厂基线。

差别的本质只有一句：**`.ndf` 里写着的是名字和枚举名，`.ndfbin` 里存的是哈希和整数。** 下面第 4 节逐项列出这个落差，以及每一处怎么补。

## 1. 产物要有什么

参考 HTML 的结构（已实测提取）：

| 章节 | 内容 | 数据依赖 |
|---|---|---|
| 0. 概览 | 9 个卡片：装备总数、有 pack、无 pack、仅载具、pack 总数、pack 被引数、孤儿 pack、AG 牌组数 | 装备 × pack × 牌组，三个集合的交叉 |
| 1. 分类统计 | 各国「有 pack / 仅载具 / 无 pack」矩阵（最有行动价值）、按 `UnitRole`（19 种）、按 `TypeStrategicCount`（35 种）、按国家/联盟 | 装备的元数据 + pack 归属 |
| 2. 装备速查 | 2911 行 × 若干列，可搜可筛可排序 | 装备 + 它的 pack 数 |
| 3. Pack 速查 | 2685 行，含引用的装备 / 载具 / Xp / 被几个牌组用 | pack + 牌组 |

一句话概括这份表的用途：**回答「这件装备能不能进将军模式、不能的话缺什么」**。

## 2. 依赖的 ndfbin 文件清单

### 2.1 权威依据不是猜的：`Config.ini`

每个 mod 根目录有一个 `Config.ini`，它的 `[Config]` 段列出**这个 mod 实际覆盖了哪些文件**：

```ini
[Config] ; Used for mod compatibility check, do not modify
GFX/Deck=7cfc42200538e097a3ea1043ae5d601e
GFX/Unit=98cb835f3ddcd279dffea9ee18e119a0
GFX/Weapon=a295ea541c9d5a6e3fe9acad7615bd85
...
```

**这一份清单有三个用处**（实现时都要用到）：

1. **判断哪些文件有效** —— mod 目录里可能有不在清单里的历史遗留文件。
   实测本 mod 有两个 Deck：`Gen/NDF/GFX/Deck.ndfbin`（在清单里，5415 个 pack）
   与 `Gen/NDF/Deck.ndfbin`（**不在清单里**，5248 个 pack，时间戳旧 5 天）。
   读错那个，数字整个偏离。
2. **判断缺什么** —— 不在清单里 = 这个 mod 没覆盖 = 需要从基线补。
3. **校验** —— 值是文件内容哈希，可用于确认读到的文件没被替换过。

### 2.2 必需文件（2 个）

| 逻辑路径 | 物理路径 | 提供什么 |
|---|---|---|
| **`GFX/Unit`** | `Gen/NDF/GFX/Unit.ndfbin` | 装备主体（`TEntityDescriptor` 4626 个）+ 它的模块（UI 元数据、类型元数据、编成元数据） |
| **`GFX/Deck`** | `Gen/NDF/GFX/Deck.ndfbin` | AG pack（`TDeckPackDescriptor` 5415 个）+ 牌组（`TDeckDescriptor` 2267 个） |

**只需要这两个。** 参考脚本读 5 个 `.ndf`（Unite / Building / StrategicPacks / StrategicDecks / DeckPacks），到了 ndfbin 侧合并成 2 个 —— 因为编译产物把同类对象打进同一个容器：

| `.ndf` 源 | 落到哪个 ndfbin | 类 |
|---|---|---|
| `UniteDescriptor.ndf` | `GFX/Unit` | `TEntityDescriptor`（`ClassNameForDebug` = `Unit_*`） |
| `BuildingDescriptors.ndf` | **同一个 `GFX/Unit`** | `TEntityDescriptor`（=`Building_*`，13 个 FOB） |
| `StrategicPacks.ndf` | `GFX/Deck` | `TDeckPackDescriptor` |
| `StrategicDecks.ndf` | `GFX/Deck` | `TDeckDescriptor` |
| `DeckPacks.ndf`（遭遇战） | 待确认（可能在 `GFX/Skirmish`） | 只用来报一个数量，非核心 |

> ⚠️ **本 mod 的 `GFX/Unit` 里混着非装备对象**：`Big_District` / `HLM_District` /
> `Mid_District` / `Small_District` 这 4 个也是 `TEntityDescriptor`，但它们不是装备。
> 判定口径：`ClassNameForDebug` 以 `Unit_` 或 `Building_` 开头才算。

### 2.3 可选文件

| 文件 | 用途 | 缺了会怎样 |
|---|---|---|
| `Gen/**/*.dic`（本地化词典） | `NameToken`（loc_hash）→ 可读词条 | 少一列「游戏内显示名」，主显示名不受影响（见 4.1） |
| `GFX/Skirmish` | 遭遇战 pack 计数（「另有一套 N 个，不属于 AG」） | 少一句说明，不算错 |

### 2.4 缺文件怎么办：mod 只有 diff

**这是必须提前对齐的边界。** mod 不保证包含全部文件 —— 它只包含改过的那些。

实测对比：

| mod | `Config.ini` 覆盖 | 有 `GFX/Unit`？ | 能否单独导出 |
|---|---|---|---|
| `A World in Flames` | 15 项 | ✅ | ✅ 可以 |
| 柏林 1989（本地 AG mod） | 6 项（Deck / Depiction / Division / Pawn / BattleOrder / Components） | ❌ | ❌ 不行 |

柏林 mod 只改 AG 相关文件，装备与 pack 全用原版 —— 它的目录里根本没有 `Unit.ndfbin`。

**补全的选项**（需要拍板，见 §6 决策 3）：

- **A. 只支持自带文件的 mod**（推荐先做）。缺文件时明确报错：「这个 mod 没有 `GFX/Unit`，它没改装备；要用基线出表请用现有工具」。工作量最小，且覆盖本次的真实目标。
- **B. 叠加 `base.zip`**。`Mods/ModData/base.zip` 存在（4564 个条目），但**里面全是 `.ndf` 源码，没有 `.ndfbin`**。所以 B 意味着同时维护两套解析器（二进制 + 文本正则），成本和风险都上一个台阶。
- **C. 读游戏本体的 ndfbin**。游戏数据封在 `Data/PC/*.dat`（Eugene bigfile），需要解包 —— 本项目目前没有这个能力。

## 3. 数据流

```
mod 根
 ├─ Config.ini ──────────────► 决定读哪些文件、缺哪些
 ├─ Gen/NDF/GFX/Unit.ndfbin ─┐
 │                            ├─► 装备表（4620 条）
 │                             │     TEntityDescriptor → ModulesDescriptors
 │                             │       ├─ TUnitUIModuleDescriptor  （UI 元数据）
 │                             │       ├─ TTypeUnitModuleDescriptor （阵营/国家）
 │                             │       └─ TFormationModuleDescriptor（编成）
 ├─ Gen/NDF/GFX/Deck.ndfbin ─┤
 │                            └─► pack 表（5415 条）+ 牌组（2265 个 AG 牌组）
 └─ Gen/Localisation/**/*.dic ──► 词条（可选，覆盖 17%）
                                    ▼
                        交叉 → 一张 HTML（内嵌 JSON，可搜可筛）
```

**JOIN 的两条边，类型不一样**（这是实现时最容易写错的地方）：

| 边 | 字段 | 类型 | 怎么连 |
|---|---|---|---|
| pack → 装备 | `UnitDescriptor` / `TransporterDescriptor` | **`trans_ref`（路径字符串）** | 取路径末段 `Descriptor_Unit_XXX`，与装备的 `"Descriptor_" + ClassNameForDebug` 比 |
| 牌组 → pack | `DeckPackList` 的项 | **`obj_ref`（object_id）** | 同一文件内按 id 直接关联 |

`trans_ref` 是字符串路径（`$/GFX/Unit/Descriptor_Unit_2K11_KRUG_DDR`）——**不需要跨文件解 id**，这一点比预想的简单。

## 4. `.ndf` → `.ndfbin` 的落差（逐项）

实测全部字段的宿主与类型（`Unit.ndfbin` / 4626 个 `TEntityDescriptor`）：

| 概念 | `.ndf` 里 | `.ndfbin` 里 | 宿主类 | 覆盖 | 结论 |
|---|---|---|---|---|---|
| 装备名 | 对象名 `Descriptor_Unit_X` | **没有对象名** | — | — | 用 `"Descriptor_" + ClassNameForDebug` 重建 |
| `ClassNameForDebug` | 字符串字面量 | `strg_ref` | `TEntityDescriptor` | **4626/4626** | ✅ 100% 可读，作主显示名 |
| `NameToken` | `'SomeToken'` | **`loc_hash`（0x1d）** | `TUnitUIModuleDescriptor` | 3686 | ⚠️ 不可逆，靠 `.dic`（见 4.1） |
| `UnitRole` | `'Artillery'` | `strg_ref` | `TUnitUIModuleDescriptor` | 3634 | ✅ 直接可读 |
| `MenuIconTexture` | `'Texture_RTS_H_x'` | `strg_ref` | `TUnitUIModuleDescriptor` | 3634 | ✅ 直接可读 |
| `PriceCategory` | `'A'` | `strg_ref` | `TUnitUIModuleDescriptor` | 3634 | ✅ 直接可读 |
| `TypeUnitFormation` | `'Tank'` | `strg_ref` | `TFormationModuleDescriptor` | 2896 | ✅ 直接可读 |
| `MotherCountry` | `'BEL'` | `strg_ref` | `TTypeUnitModuleDescriptor` | 3686 | ✅ 直接可读 |
| **`Coalition`** | `TWargameCoalition/NATO` | **`int32`** | `TTypeUnitModuleDescriptor` | 1545 | ⚠️ 需枚举表（见 4.2） |
| **`TypeStrategicCount`** | `ETypeStrategicDetailedCount/Supply` | **`int32`** | `TUnitUIModuleDescriptor` | 3500 | ⚠️ 需枚举表（见 4.2） |
| pack → 装备 | `Unit = $/GFX/Unit/X` | `trans_ref` 路径 | `TDeckPackDescriptor` | 5415 | ✅ 解析路径末段 |
| pack 的 `Xp` | `Xp = 2` | `int32` | `TDeckPackDescriptor` | 4562 | ✅ |
| 牌组 → pack | `~/(Descriptor...Pack_X,)` | `obj_ref` | `TDeckDescriptor.DeckPackList` | 2267 | ✅ 同文件按 id |

### 4.1 `NameToken` 是哈希：能解 17%

`.dic` 是 mod 自带的本地化词典，`tradic.read()` 可读。实测本 mod：

```
26 个 .dic（COMPANIES / INTERFACE_INGAME / INTERFACE_OUTGAME / PLATOONS / UNITS）
UNITS 家族 968 条，PLATOONS 家族 0 条
装备 3686 个有 NameToken，能被解出的 643 个 → 17%
```

**原因**：游戏原版的词条字典封在 `Data/PC/*.dat` 里，mod 只带自己新增的词条。
这不是 bug，是数据边界。

**所以主显示名必须是 `ClassNameForDebug`**（100% 可得），词条名只作附加列
（有就显示，没有留空）。参考 HTML 里 `name`（词条）与 `cn`（ClassName）本就
是两列，这里只是让 `cn` 升为主键。

> 附带好处：`ClassNameForDebug` 在 mod 里是**作者自己写的可读名**
> （`Unit_2K11_KRUG_DDR`、`WF_VDV_HMG_RU`），比哈希解出来的通用名更贴近 mod 语境。

### 4.2 两个枚举字段是整数：需要一张映射表

| 字段 | 实测取值 |
|---|---|
| `Coalition` | 只有 `1` 一个值（1545 个对象）—— 本 mod 全是同一阵营 |
| `TypeStrategicCount` | **34 种**，`1..35`（缺 34），最大宗是 1（113）/2（101）/12（520） |

`.ndf` 里它们是 `TWargameCoalition/NATO` 这种路径名，`.ndfbin` 里只剩整数。
要显示「炮兵」「补给」这类中文/英文名，必须有一张 `整数 → 名字` 的表。

**这张表从哪来**（需拍板，见 §6 决策 4）：

- **硬编码**：`Coalition` 只有 2~3 个值、`TypeStrategicCount` 35 个，抄一次就够。缺点：游戏更新加值时要人改。
- **从 `base.zip` 的 `.ndf` 里提**：`UniteDescriptor.ndf` 里满是 `ETypeStrategicDetailedCount/Supply` 字面量，可以扫出「出现过哪些名字」，但**拿不到「名字 ↔ 整数」的对应**（ndf 里是名字，没有数字）。
- **从游戏枚举定义里提**：本项目的 ndfbin 解码器目前不解析 enum 定义表，需要先确认 ndfbin 里到底有没有这张表。

**倾向**：先硬编码，并在表里标注「来源：实测 + 人工核对」；发现对不上再改。

## 5. 实测数据（`A World in Flames`，2026-10-19）

跑通 JOIN 后的真实数字，可作为实现后的对照基准：

```
输入
  Unit.ndfbin      56,223 对象 / 102 类      650 KB
  Deck.ndfbin      60,112 对象 /   5 类      563 KB
  .dic             26 个（UNITS 968 条）

装备
  TEntityDescriptor         4,626
    → 装备口径（Unit_ + Building_）  4,620   （4 个 *_District 排除）
        Unit_    4,609
        Building_   13   （FOB，混在同一个文件里）
  ClassNameForDebug 覆盖    4,626/4,626 = 100%

Pack
  TDeckPackDescriptor       5,415
  → 指到装备的               5,414  （精确 5,390 + 剥前缀兜底 24）
  → 悬空引用                     1  （`Descriptor_Unit_WF_VDV_HMG_RUS`，
                                      装备里只有 `..._RU` —— mod 自身笔误）

牌组
  TDeckDescriptor           2,267
  → 带 DeckIdentifier（AG）  2,265
  → 引用到的不同 pack        3,530
  → 孤儿 pack（没牌组用）    1,885   （参考基线是 0；本 mod 大概在攒素材）

装备 × pack 交叉（校验 2247 + 317 + 2056 = 4620 ✅）
  有 pack              2,247
  仅作载具               317
  完全无 pack          2,056   ← 「装备选择器里选不到」的那些
```

**一个必须解释清楚的反差**：参考 HTML 是「2911 装备 / 1291 无 pack」，
本 mod 是「4620 装备 / 2056 无 pack」。前者读原版基线，后者读一个加了
一千多件新装备的 mod。**这正是这个功能存在的理由** —— 你想看的是后者。

另外「孤儿 pack 1885」不是错误：本 mod 有大量定义好但还没铺进牌组的 pack。
参考基线是 0（原版不会留白）。这一栏的语义应写成「定义了但没牌组引用」，
而不是「有问题」。

## 7. 建议的实现路径

**第一步：内核 + CLI（不碰 GUI）**

新增 `ndfbin_decks/ndfedit/equip_lookup.py`，一个函数出数据：

```python
build_lookup(mod_root: Path) -> Lookup
#   Lookup.equipments : list[Equipment]   装备（含 pack 计数、载具计数）
#   Lookup.packs      : list[Pack]        pack（含被几个牌组引用）
#   Lookup.decks      : int               AG 牌组数
#   Lookup.dangling   : list[str]         pack 指向了不存在的装备
#   Lookup.notes      : list[str]         数据口径问题（如「有 X 个悬空引用」）
```

**关键要求：所有「对不上」都要收集起来，不能静默丢弃。** 这次勘察就撞到 1 个
悬空引用（`WF_VDV_HMG_RUS`）和 24 个需要剥前缀才连上的 FOB —— 这类条目如果
静默跳过，用户会看到「装备数少了一件」却不知道为什么。

**第二步：HTML 渲染**

直接把参考 HTML 当模板（它已是单文件、内嵌 JSON、无外部依赖），
把数据源从「`.ndf` 正则」换成 `Lookup` 对象。样式与版式不用重做。

**第三步：GUI 入口**

主界面加一个菜单项「导出速查清单…」，选 mod（复用 `modpicker`）→ 选保存路径 →
生成。**要能显示「读了哪些文件、缺了哪些、有多少条对不上」**，而不是默默出一个 HTML。

## 8. 验收标准

| # | 项 | 怎么验 |
|---|---|---|
| 1 | 装备数与 `ClassNameForDebug` 口径一致 | `A World in Flames` → 4620（4609 Unit + 13 Building） |
| 2 | pack → 装备 命中率 ≥ 99% | 5414/5415；剩下的必须列在「悬空引用」里，不能静默消失 |
| 3 | 交叉表自洽 | 有 pack + 仅载具 + 无 pack == 装备总数（2247+317+2056=4620） |
| 4 | 只读有效文件 | `Gen/NDF/Deck.ndfbin`（不在 Config 清单里）不被读入；pack 数应为 5415 而非 5248 |
| 5 | 缺文件时给人话 | 柏林 mod → 「这个 mod 没有 GFX/Unit」+ 一句怎么办，不崩 |
| 6 | 只读不写 | 导出全程 `dirty_count() == 0`，不碰 mod 文件 |
| 7 | 产物可离线打开 | 单文件 HTML，断网可用，搜索/排序/筛选都能用 |

---

## 9. 明确不做的

- **不解析 `.ndf` 源码**（除非决策 3 选 b）。那是另一套解析器，与「从 ndfbin 读」的初衷相悖。
- **不解 `Data/PC/*.dat`**（Eugene bigfile 解包），工作量与收益不成比例。
- **不写回 mod**。这是只读导出，不涉及保存、撤销、备份那一套。
- **不做词条翻译**。只把已有的 `.dic` 条目列出来，缺的留空。

---

## 10. 一句话总结

**两个必需文件（`GFX/Unit` + `GFX/Deck`）、一张 `Config.ini` 清单、三处需要额外数据的落差（词条哈希 / 两个枚举 / 24 个 FOB 的前缀差异）。** 其余都是现成的：解码、字段读取、JOIN 都有可复用的代码，参考 HTML 可以直接当模板。
